# 二改功能清单

本文档描述相对官方基线 `vendor-0.1.185` 的有效二改需求。文件级实现范围以
`.github/custom-upstream-delta.tsv` 为准。

## 1. 内容审计范围隔离

### 目标

官方 `cyber_policy` 处罚仅对管理员配置的审计分组生效。范围外请求仍保留必要
的安全审计记录，但不得通知、累计违规次数、封号或写入会话屏蔽。

管理员配置的原“审计范围”作为总审计范围，继续共同约束关键词拦截、API 审计和
`cyber_policy`。API 审计可在总范围内单独选择全部或指定分组，不得扩展到总范围外。

### 行为约束

- 范围内保持官方处罚语义。
- 范围外记录 `action=cyber_policy_out_of_scope`。
- 范围变化必须在下一次请求生效。
- 总范围选择全部分组时，关键词拦截覆盖全部分组；选择指定分组时，只覆盖所选分组。
- “关键词 + API”在总范围内先执行关键词拦截，仅在 API 子范围内继续调用审核 API；
  “仅 API”只在 API 子范围执行；“仅关键词”保留 API 子范围配置但不调用审核 API。
- API 指定范围必须非空且为总范围子集；缺少 `api_audit_scope` 的旧配置按“总范围内
  全部分组”解释，保持升级前行为。
- 分组删除后，管理页面加载时剔除已删除的历史范围引用；保存时后端再次收敛持久化配置
  中继承的失效 ID，避免孤儿引用阻塞其他审计设置修改。新提交的不存在分组仍拒绝保存，
  分组查询异常不得伪装成“分组不存在”。
- 总范围指定模式允许保持空分组列表，表示关键词与 API 均不覆盖任何分组，兼容既有配置。
- 模型过滤保持既有语义，位于关键词和 API 判断之前，同时约束两者，不改为仅约束 API。
- 异步审核 worker 必须读取最新配置并再次检查 API 子范围，范围移除后不得继续调用 API。
- 关键词命中摘要必须脱敏，不记录 Token、密钥、完整 URL 或完整请求体。
- 管理页面必须分别显示总审计范围、API 审计范围和当前状态。
- Custom 管理页面必须同步官方内容审核代理配置：代理列表加载失败不阻塞页面，保存配置
  与 API Key 测试必须携带同一个 `proxy_id`，`0` 表示清除代理并恢复直连。

### API 审计独立封禁阈值

默认封禁触发次数继续统计关键词、API 审计及未被排除的 `cyber_policy` 命中。管理员
可以额外启用一个全局 API 审计封禁阈值；API 审计命中同时进入默认总累计和 API
专属累计，任一规则达到阈值即自动封禁，因此专属规则只能收紧、不能放宽默认规则。

- `api_audit_ban_enabled` 控制专属规则，`api_audit_ban_threshold` 必须为 `1-1000`；
- 旧配置缺少字段时专属规则关闭，专属阈值按当前默认封禁阈值初始化；关闭规则或自动
  封禁总开关时保留阈值但不执行专属处罚；
- API 专属累计包含审核 API 产生的 `flagged=true` 且 `action=allow|block` 记录，以及
  `flagged=true` 的范围内 `cyber_policy` 命中；不包含关键词、hash、范围外、错误或未命中记录；
- 专属累计与默认累计共用累计窗口，并从最后一条 `auto_banned=true` 记录之后重新起算；
  保存配置不扫描历史或立即封号，仅在下一次 API 审计或范围内 `cyber_policy` 命中时包含窗口内历史并判定；
- 默认累计先达到或两条规则同时达到时保持默认规则的次数和阈值；仅专属规则先达到时，
  触发日志和封禁通知显示 API 专属次数与阈值。两条规则只执行一次账号禁用、缓存刷新
  和封禁通知，管理员豁免不变；
- 用户专属封禁阈值只覆盖默认总累计阈值，不覆盖全局 API 专属阈值；配置继续保存在
  `content_moderation_config` JSON 中，不新增 Migration、Schema 或 SQL 表字段。

### 用户专属封禁阈值

“默认封禁触发次数”继续适用于未单独配置的用户。管理员可以按用户 ID 配置一个
`1-1000` 的绝对阈值；命中用户始终使用该值，不随默认阈值变化。用户项必须唯一，
删除专属项后立即恢复默认值。

- 专属配置只覆盖触发次数，累计窗口、计数来源、`cyber_policy` 排除开关和自动封禁
  总开关保持全局配置；
- 保存配置不扫描历史违规记录，也不立即封禁用户；仅在该用户下一次命中时判定；
- 普通内容审计与 `cyber_policy` 处罚使用相同解析规则，命中提醒、封禁邮件和
  `{{ban_threshold}}` 模板变量显示实际阈值；
- `cyber_policy` 排除自动封禁计数时，命中提醒仍按用户独立解析实际阈值，但不读取
  违规累计次数，也不触发处罚逻辑；
- 管理员账户仍不自动封禁；已删除或缺失用户的历史配置保持可回显、可移除且运行时
  自然失效，不阻塞其他配置保存；
- 配置保存在现有 `content_moderation_config` JSON 中，旧配置缺少
  `user_ban_thresholds` 时按空列表处理，不新增 Migration、Schema 或 SQL。

### 主要实现

```text
backend/internal/custom/moderation/
backend/internal/service/custom_moderation_bridge.go
frontend/src/custom/moderation/
```

## 2. 固定公开 Release 更新源

### 目标

在线更新、版本查询和回退固定使用：

```text
o87110/sub2api-custom-public
```

调用方不能通过环境变量、请求参数或缓存内容切换仓库。官方仓库只用于显示官方
版本信息，不能作为自定义构建的安装回退源。

### 公开访问

公开 Release 元数据和资产默认匿名读取。`UPDATE_GITHUB_TOKEN` 与
`UPDATE_GITHUB_TOKEN_FILE` 仅用于提高 GitHub API 限额或兼容受控部署；未配置
Token 不应导致公开更新失败。

配置 Token 时仍必须满足：

- 只发送到精确 HTTPS `api.github.com`；
- 重定向到资产存储主机前删除 Authorization；
- Token 文件优先于环境变量；
- Token 文件配置错误时明确失败，不能静默改用环境变量；
- 日志、错误和浏览器响应不得出现 Token。

### 下载约束

- 资产 URL 必须属于固定仓库和受信任 GitHub 主机。
- 标签必须符合 `vX.Y.Z-custom.N`。
- 二进制与 `checksums.txt` 必须同时存在。
- 下载大小受限并校验 SHA256。
- 解压目标必须防止路径穿越和符号链接攻击。
- 新二进制必须通过 `--version` 验证后才允许替换。

## 3. 基础版本与构建版本分离

版本面板同时展示：

- 基础版本：`X.Y.Z`，用于与官方正式版本比较；
- 构建版本：`X.Y.Z-custom.N`，用于自定义更新和回退；
- 官方最新版本及独立查询警告。

自定义版本比较必须使用完整构建版本。官方查询失败不能覆盖已经取得的自定义
Release 信息；自定义源失败也不能回退安装官方资产。

缓存必须包含仓库标识和完整构建版本，拒绝跨仓库、旧格式或受污染缓存。

## 4. 在线更新二进制持久化

容器镜像中的 `/app/image/sub2api` 是只读基线，运行二进制保存在：

```text
/app/runtime/sub2api
```

首次启动从镜像初始化 runtime；local Compose 使用宿主机 `./runtime`，
standalone Compose 使用 `sub2api_runtime` 命名卷，容器重建继续使用已验证的
runtime 文件。更新使用原子替换，保留一个可回退备份，失败时恢复原可执行文件。
入口脚本必须拒绝 runtime、镜像、旧镜像和备份路径（包括悬空链接）本身为符号
链接，并在版本探测、复制、替换和执行前再次检查。

## 5. 可验证 Release 与 GHCR

发布标签格式为 `vX.Y.Z-custom.N`。正式发布必须：

- 绑定准确 Tag、提交和已通过的 CI；
- 一次构建生成 Linux `amd64`、`arm64` 归档及 OCI Layout；
- 生成 `checksums.txt` 和不可变 Release Manifest；
- 校验 Artifact ID、Digest、文件清单和 OCI Manifest；
- 使用完整版本 GHCR 标签，不发布可漂移的 `latest`；
- 不覆盖已发布资产，不移动已有 Tag；
- Release 和 GHCR 任一不完整时视为不可部署。

公开仓库的 GitHub Release 与当前 GHCR Package 均支持匿名访问。GHCR 可见性独立
于仓库可见性，发布后必须确认 Package 仍为 Public；只有未来明确改为 Private 时
才启用文档中的条件拉取鉴权。

## 6. 官方升级隔离

- `main` 保存二改主线。
- `upstream/main` 表示官方远程尚未审核的最新主线，不作为当前基线。
- `origin/upstream/main` 保存本仓库已经审核的官方镜像提交。
- `vendor-X.Y.Z` 标记已审查并合入的官方基线。
- `upgrade/vX.Y.Z` 保存可复现的升级现场。

升级必须检查冲突、二改保护路径、影子来源、数据库语义、后端测试、前端测试和
Release 预构建。失败分支不得重置或强推，以便继续修复和审查。

## 7. 数据库与差异门禁

`.github/custom-upstream-delta.tsv` 固定当前二改文件集合、Blob 和验证方法；
`.github/custom-database-exceptions.tsv` 只允许经过说明的数据库边界例外。

普通变更和官方升级都必须阻止：

- 未登记的 Migration 或 Schema 变化；
- 保护路径被官方升级静默覆盖；
- 影子来源重新进入运行时而绕过 Custom 实现；
- 生成代码未更新；
- 台账与候选 Tree 不一致。

## 8. API 密钥当前页批量操作

用户 API 密钥列表支持勾选当前页密钥，并执行以下操作：

- 批量切换到一个当前可用分组，不支持批量解除分组；
- 所选密钥全部停用时，状态按钮自动切换为“批量启用”，确认后立即恢复调用能力；
- 只要选择中存在活跃密钥，状态按钮保持“批量禁用”；只禁用活跃项，`inactive`、
  `expired` 和 `quota_exhausted` 等非活跃状态均保持原状并按通用跳过数量提示；
- 批量删除，执行前必须进行危险操作二次确认。

批量启用和禁用都需要二次确认；启用确认使用非危险样式，禁用和删除保留危险
提示。批量请求复用单密钥更新和删除接口，最多同时执行 5 个请求；不提供事务
回滚。成功或已经满足目标的密钥从选择中移除，失败项保留选中供重试，前端只
显示成功、跳过和失败数量，不暴露密钥值或后端敏感错误。

选择范围固定为当前页。分页、页大小、筛选、排序或手动刷新会清空选择；不支持
跨页累计选择或直接选择全部筛选结果。删除当前非首页的全部行后回退到上一页。

主要实现：

```text
frontend/src/custom/api-keys/
frontend/src/views/user/KeysView.vue
```

## 9. 支付宝/微信多渠道用户选择

管理员可以同时启用易支付与官方支付宝/微信实例。充值和订阅页按服务商聚合并
展示以下稳定渠道：`easypay_alipay`、`official_alipay`、`easypay_wxpay`、
`official_wxpay`；同一渠道的多个实例继续由现有负载均衡策略分配。

- 默认顺序固定为易支付支付宝、官方支付宝、易支付微信、官方微信，再到 Stripe、
  Airwallex 和自定义方式；
- 新前端通过 `payment_type + provider_key` 精确选源，旧客户端不传
  `provider_key` 时保留后台默认来源逻辑；
- 币种、费率、单笔限额和每日限额只在同一渠道内聚合，单笔限额按本金加手续费后的
  网关实付金额判断；同渠道多实例存在不连续单笔区间时通过增量
  `amount_ranges` 保留各安全区间，旧客户端只看到首个连续区间，混合币种只隐藏
  受影响渠道；
- 显式渠道的全部实例均超过限额时失败关闭，不回退到超限实例；旧客户端不传
  `provider_key` 时继续保留原路由兼容行为；
- 实例选定后保存运行配置修订指纹，下单前及调用网关前重新确认实例仍启用且配置
  未变化；金额限额复核无法查询当前用量时失败关闭；
- 前端金额、手续费与订阅汇率换算按渠道币种最小单位进行精确十进制舍入，零小数
  币种拒绝小数金额，BHD、KWD、JOD 等三位小数币种允许三位小数输入；
- 网关失败只提示用户手动切换可见备用渠道，不自动跨渠道创建第二个订单；
- 移动端同一渠道转二维码、微信 OAuth/JSAPI 和恢复令牌保持原 `provider_key`；
- 旧后端没有 `method_options`、旧恢复快照或旧微信令牌没有渠道字段时继续兼容；
- 支付设置通过现有 settings 表中的 `PAYMENT_CHANNEL_SETTINGS` 保存“用户渠道配置”，
  不修改数据库结构。配置按稳定渠道 ID 聚合，覆盖支付宝、微信、Stripe、
  Airwallex 和易支付自定义方式，同一渠道多个实例共享一份配置；管理设置接口使用
  `payment_channel_settings`，独立支付配置接口使用 `channel_settings`；
- 管理员可为每个用户渠道设置一个跨语言通用的显示名称；留空使用系统多语言名称。
  自定义名称只用于充值、订阅选择器和备用渠道提示，不改路由、签名、订单标识或
  历史订单展示；服务商实例名称仍只供管理员识别；
- 全局充值费率改为“默认支付手续费率”，同时作为余额充值和订阅的默认值。渠道
  费率留空或 `null` 时继承默认值，显式 `0` 表示免手续费，其他值限制为
  `0–100` 且最多两位小数；
- 新客户端显式传递 `payment_type + provider_key` 时，余额充值、订阅换算、限额
  判断、订单保存和微信 OAuth/恢复流程使用渠道最终费率；微信 OAuth 使用短期签名
  上下文冻结本次费率，恢复令牌继续携带该值。旧客户端不传 `provider_key` 时继续
  使用全局默认费率，旧恢复令牌没有费率字段时继续按旧逻辑计算；
- 未知但格式合法、当前无实例的渠道配置会保留，渠道重新创建后恢复生效；非法
  ID、名称、费率或畸形持久化 JSON 严格拒绝；
- EasyPay 支持通过自定义类型映射接入额外方式，例如 `usdt_trc20 -> usdt`；CID
  按映射后的上游 `type` 选择，只有 `alipay*`/`wxpay*` 使用专用 CID，其他类型
  只使用通用 CID；
- EasyPay 自定义 `type` 禁止 `alipay`、`wxpay`、`stripe`、`card`、`link` 及
  `alipay*`/`wxpay*` 前缀，避免与内置渠道归一化和实例路由冲突；`easypay`、
  `airwallex` 不在本次禁止范围内；
- 同一旧版支付方式的多个 EasyPay 实例仅在所有非空展示名一致时返回该名称，
  出现冲突时返回空名称；该规则与新版 `method_options` 一致；
- EasyPay 的 USDT 方式仍是外部兼容服务的自定义类型映射，不提供原生 TRC20
  钱包地址生成、交易哈希查询、区块确认或链上到账监听；
- 本功能不新增 Migration、Schema、实体字段或 SQL。

主要实现：

```text
backend/internal/custom/paymentchannels/
frontend/src/custom/payment-channels/
```

后端渠道目录、订单准备、实例选择、订单/恢复策略和实例修订复核由 Custom 协调器
负责；前端定价、渠道重选、同渠道二维码回退和手动备用提示由 Custom composable
负责。官方 Service 与页面只保留查询/签名/DTO 适配，以及在“持久化前准备”和“网关
调用前复核”两个生命周期点分别委托 Custom。provider-agnostic 微信请求最终选中官方
`wxpay` 时，会补载 OAuth AppID 后再执行实例兼容性校验。

### 支付回调与订单状态补偿

- 支付回调仍是首选路径，但 `PENDING` 订单会由后台任务按批次主动查询所有已配置
  支付渠道，不再只依赖微信回调；近期 `EXPIRED`/`CANCELLED` 订单也会在迟到支付
  恢复窗口内复核，漏回调时按统一通知和履约流程补单；
- 上游查询失败、返回空响应、实例配置无法解析或支付金额/商户身份校验失败时，订单
  不会被强制标记为已支付，也不会被静默标记为取消/过期，后台会保留重试机会并记录
  告警；金额和商户元数据校验不因补偿查询而放宽；
- 上游明确返回终态失败时直接按未支付处理，不再重复调用已关闭交易的取消接口，
  本地取消或超时任务可以继续释放订单占用；只有上游仍为 `pending` 时，关闭失败才
  延迟本地状态变更并保留重试；
- 用户或管理员取消使用条件更新。支付通知、超时任务或其他取消请求抢先改变状态时，
  取消接口返回冲突而不是伪造“取消成功”；上游状态暂时不可查询或关闭失败时不确认
  本地取消；

## 11. 分组最低余额门槛

## 12. 套餐限量销售与售罄处理

管理员可为订阅套餐设置当前剩余可买数量。`NULL` 表示不限量，现有套餐迁移后保持
`NULL`，不会因升级改变销售行为。每个套餐可选择 `delist`（自动下架，默认）或
`disable_purchase`（保留展示并禁用购买）作为售罄处理方式。

- 创建待支付订阅订单时在同一数据库事务内预占一份库存；条件更新保证并发请求不能
  把数量扣成负数。最后一份被预占后，`delist` 套餐自动下架，
  `disable_purchase` 套餐保持展示但不能继续购买或续费；
- 订单取消、超时或支付单创建失败时，仅将 `reserved` 预占释放一次。由售罄自动
  下架的套餐恢复上架，管理员手动下架的套餐保持下架；
- 支付成功并发放订阅时在同一事务内将预占转为 `consumed`，履约重试不重复扣减；
  已释放订单延迟付款时重新尝试预占，无库存则履约失败，补货后可沿用现有重试；
- 订单创建时为不限量的套餐记录为 `untracked`，之后开启限量不追溯旧订单；全额和
  部分退款均不归还已消费数量；
- 管理更新数量采用三态语义：省略表示不修改，`null` 改为不限量，整数设置当前
  剩余数量；只有最终策略为 `disable_purchase` 时才允许管理员填写 `0`；
- 自动下架套餐补货、改为不限量或在售罄时切换为 `disable_purchase` 后自动恢复展示；
  `disable_purchase` 售罄套餐切换为 `delist` 时立即自动下架。管理员手动下架始终
  优先，不因补货或策略切换自动恢复；
- 管理表格显示“无限制”、正整数或“0 / 已售罄”，并区分自动下架与禁用购买。
  用户接口只暴露派生的 `sold_out`，不公开精确正数库存；售罄可见卡片显示“已售罄”
  且购买/续费按钮不可操作。页面加载后若库存被并发抢空，前端识别
  `PLAN_SOLD_OUT`/`PLAN_NOT_AVAILABLE`，重新获取权威套餐列表并清除失效选择；刷新失败
  时也会本地禁用或移除对应套餐。后端原子预占继续阻止绕过前端的超卖请求；
- 本功能新增 Migration `194_subscription_plan_inventory.sql` 和
  `195_subscription_plan_sold_out_action.sql`、Ent Schema 字段及生成代码。Migration
  195 默认 `delist`，历史套餐行为不变。发布前必须人工审核 Migration、备份
  `subscription_plans`/`payment_orders` 并通过数据库边界门禁；开发和测试过程不得
  连接或修改生产数据库。

## 13. 订阅本周期累计、手动重置次数与套餐批量重置

后台订阅管理、用户“我的订阅”和顶部“我的订阅详情”在订阅发生过手动额度重置后，
紧凑显示：

```text
本周期累计 $X · 已重置 N 次
```

- `manual_quota_reset_count = 0` 时整行不显示，但累计用量仍在后台持续记录；
- 现有“重置用量配额”仍同时清空所选日/周/月窗口用量，并将手动重置次数原子加一；
  `cycle_usage_usd` 不随手动重置清空，两个统计字段不参与任何限额判断；
- 正常使用产生的订阅实际费用同时累加到窗口用量和本周期累计，历史 `usage_logs`
  保持不变；迁移时使用现有窗口最大值与可用历史日志合计中的较大值回填；
- 提前续订继续只延长订阅最终 `expires_at`，不改变当前开始/结束日期、窗口用量、累计
  或重置次数。续订周期按顺序排队，只有原周期真正到期并进入下一周期时，才归档旧
  累计与次数并清零新周期统计；
- 管理员延长已过期订阅时会重新激活最后一个已归档周期；退款扣减只调整最后一个统计
  周期。扣减会在同一事务内锁定订阅和周期、捕获快照，并在需要过期时完成撤销；网关
  退款失败仅在订阅状态、删除时间、当前周期边界及全部周期后置状态均未变化时精确恢复，
  避免覆盖并发续订或周期推进；
- 管理员重置支持可选 `Idempotency-Key`，Header 会先按统一规则规范化再求 Hash。单项
  幂等声明、周期边界推进、日周月清零和次数加一位于同一事务；外层响应保存失败或进程
  中断后的同键重试不会再次增加次数。新前端失败重试复用同一键，旧客户端无键调用保持
  兼容。事务内声明由外层接口 Scope、管理员 Scope 和规范化键共同派生，并使用外层记录
  的同一过期时间；同键用于单项与批量接口时互不碰撞，外层过期重新执行时会在订阅行锁
  内原子替换已过期声明，重放则同步声明期限但不重复产生副作用。

管理员还可分别控制支付套餐与手动分配订阅的批量重置资格。套餐创建/编辑中的开关
只控制购买该套餐产生的支付订阅；手动分配时可为新周期单独开启资格，已有有效
`assignment/legacy` 周期可在订阅操作区开启或关闭。两类开关均默认关闭。订阅管理页
的“批量重置配额”弹窗会先列出候选用户、订阅来源、本周期累计和已重置次数，默认
全选，并允许逐项取消：

- 只纳入未删除、`active`、已开始且未到期的订阅；
- `payment` 当前周期必须能通过支付订单准确追溯到仍存在并开启开关的套餐；订单用户、
  订单订阅分组、套餐分组必须与当前订阅一致；
- `assignment/legacy` 当前周期只读取自己的 `manual_bulk_quota_reset_enabled`；修改该值
  不改变有效期、窗口用量、本周期累计或重置次数。调整当前周期到期日保留该值，新周期
  使用创建时提交的值且不继承旧周期；`redeem` 始终排除；
- 支付订阅提前续订只认当前周期套餐，周期边界后才改用待生效套餐；`legacy`、兑换码、
  管理员分配不会被猜测为支付套餐；只有手动资格明确开启的有效 `legacy/assignment`
  周期入选；
- 提交接口要求 `Idempotency-Key`，后端对订阅 ID 去重；每项都在同一事务中锁定订阅、
  推进周期并重新锁定校验当前周期、支付订单与套餐资格，然后才记录逐项幂等声明并重置。
  状态或资格变化记为跳过，实际重置错误记为失败，不因单项失败回滚其他成功项；若检查
  资格前已经推进到新周期，即使新周期不再符合资格，提交后也会失效 L1、Redis 和跨实例
  订阅缓存，避免旧周期用量继续参与限流；
- 每批最多提交 300 个订阅；候选超过上限时前端默认选择前 300 个并提示分批处理，确保

## 14. 分组模型调用双重黑名单

管理员可在新建、编辑分组时独立配置模型调用黑名单。新旧分组的
`models_list_config.blocked_models` 默认均为空，即默认不禁用任何模型；只有管理员
主动勾选并保存后才生效。黑名单仅对去空、去重后的模型 ID 做精确匹配，不支持通配符。

- 在分组、渠道、复合路由或账号映射前检查客户端原始模型，并在显式映射、规范化后的
  最终业务模型出网前再次检查；例如禁用 `gpt-5.4-mini` 会同时拒绝直接请求和 Haiku
  映射到 Mini 的调用，禁用 `gpt-5.6-luna` 不影响 `gpt-5.6-sol`、`gpt-5.6-terra`；
- OpenAI OAuth 生图桥为协议适配注入的 Responses 主模型属于内部编排实现，不参与调用
  黑名单；客户端请求及图片工具模型仍参与检查，因此禁用当前内部主模型不会连带禁用
  `gpt-image-2`，直接禁用 `gpt-image-2` 仍会拒绝生图；
- 账号级映射命中黑名单时跳过该账号并继续调度其他允许路径，全部持久可用路径都被策略
  排除时返回协议兼容的 `404 model_not_found`，不伪装成容量不足或 503；确定性的分组、
  渠道和复合路由映射命中时直接拒绝；
- fallback 调度使用原始分组与实际承载分组黑名单的并集，异步图片和批量图片在真正提交
  上游前重新加载策略；已发送的进行中请求不强制中断，状态查询和内容下载不受影响；
- OpenAI、Anthropic、Gemini 分别返回自身协议的 404 结构，本地策略拒绝记为
  `local_policy_denied`；模型详情路径始终优先于同名 query 参数，普通 POST/PUT 等请求以
  body 模型为准，只有明确消费模型的 Realtime GET 路由读取 `?model=`。JSON、multipart、

## 15. 管理端批量撤销邀请返利

“邀请返利 → 返利记录”支持勾选当前页最多 100 个有效返利订单，先预览每位邀请人的
资金影响，再进行整批原子撤销。分页、筛选、排序、页大小或刷新都会清空选择；已撤销
记录保留在管理端并禁用再次选择，用户端不展示也不计入累计返利或单人上限。

撤销使用固定严格追回顺序：仍冻结的目标返利从冻结额度扣除；已解冻部分优先使用当前
可用返利，不足部分直接扣邀请人余额并允许为负。只有实际扣到余额的部分减少
`total_recharged`，全部目标金额减少 `aff_history_quota`。负余额沿用官方计费语义，只
阻止余额模式请求，不取消仍有效的订阅，后续充值自然抵消负数。

执行前预览返回绑定当前返利、额度、余额和更新时间的 token；执行时重新按邀请人固定
顺序加锁并复算，预览过期、重复撤销、资金汇总不一致或任一写入失败都会整批回滚。
写接口强制 `Idempotency-Key`，成功后保存独立撤销审计，把原返利流水状态从
`accrue` 标记为 `reversed` 并清空冻结时间，同时写入
`AFFILIATE_REBATE_REVERSED` 支付审计；不删除原返利行、充值订单或原
`AFFILIATE_REBATE_APPLIED`。历史手工撤销尽力从支付审计回填，无法可靠取得的快照明确
标记为不可用。

事务提交后的认证与余额缓存失效使用独立短超时上下文；即使首次请求取消、缓存删除失败
或通用幂等层直接 replay，使用相同幂等键重试仍会按已提交撤销记录重新失效受影响邀请人的缓存。
